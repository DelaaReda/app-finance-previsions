# BATCH-28 — Frontend Dynamic UX Hardening (Freshness + Error States) [ARCH]

## Architecture plan ref
- `docs/architecture/ARCHITECTURE_MAP.md`

## Objectif
Standardiser l’UX des états dynamiques (freshness + erreurs) en s’appuyant sur des contrats API explicites et une instrumentation minimale, sans dépendances top-level inter-batch.

## Décisions d’architecture
1) Contrat UI “Dynamic State”
   - Chaque surface dynamique expose un état unique: `LOADING | HAS_DATA | EMPTY_OK | STALE | ERROR | NO_DATA_CONTRACT`.
   - `NO_DATA_CONTRACT` est réservé aux cas contractuels (pas aux trous de mapping).

2) Freshness
   - Le FE affiche `STALE` via un champ contractuel (ex: `freshness_ts`, `freshness_status`) et un fallback texte si absent.

3) Erreurs actionnables
   - Un code d’erreur stable + message utilisateur + CTA (retry) sont supportés dans les réponses API.

4) Observabilité
   - Event FE: `dynamic_state_rendered` (state, route, widget_id, correlation_id).
   - API: normalisation des payloads/erreurs dans `apps/api/runtime/`.

## Architecture audit (paths impactés)
- `apps/web/src` (composants états, widgets/facettes, telemetry)
- `apps/api/runtime/` (erreurs/normalisation)
- `apps/api/src/domains/*` (DTO/contrats)
- `platform/automation/` (preuves/gates uniquement)

## Acceptance gate
- Scénarios e2e: data ok / empty legit / stale / error.
- Preuves: capture UI + payload exemple + event/metric.

## Politique dépendances
- single batch; sequencing intra-batch uniquement (pas de depends_on_batch inter-BATCH-XX).
