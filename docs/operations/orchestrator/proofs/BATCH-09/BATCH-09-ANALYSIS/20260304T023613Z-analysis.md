## Baseline factuelle
- Flux actif: `BATCH-09-ANALYSIS` en cours, chaîne canonique planner/dev/admin.
- Cible produit: alertes actionnables fiables, visibilité monitor cohérente, livraison continue sans faux blocs.
- Contraintes: réutilisation modules/API existants, pas de duplication de stack.

## Top causes racines (style deep diagnostic)
1. Cause racine: divergence d'état entre source runtime et source de rendu monitor.
   - Symptôme: UI montre `DEGRADED/WAITING` incohérent avec workboard/queue réels.
   - Impact: mauvaise priorisation des agents, faux diagnostics de blocage.
   - Correctif minimal: forcer lecture sur chemins canoniques et horodatage fresh/stale unique.

2. Cause racine: blocages silencieux sur parsing/contract (sorties partiellement invalides).
   - Symptôme: fallback `none_no_signal` répété malgré items READY.
   - Impact: ticks consommés sans progression réelle.
   - Correctif minimal: imposer chaîne `root_cause->fix_applied->verify` et evidence stricte avant `PASS`.

3. Cause racine: états cachés stales (sessions tmux legacy, locks, caches gate expirés).
   - Symptôme: retry, contention, faux busy states.
   - Impact: cadence ralentie et erreurs difficiles à reproduire.
   - Correctif minimal: nettoyage périodique + check staleness intégré dans la boucle admin.

4. Cause racine: prompt delivery insuffisamment causal sur incidents complexes.
   - Symptôme: réponses descriptives sans fix minimal testable.
   - Impact: stagnation, régressions répétées.
   - Correctif minimal: protocole deep diagnostic obligatoire dans prompts dev/admin.

5. Cause racine: absence de format `before/after/test` dans la preuve de vérification.
   - Symptôme: correctifs non vérifiables et audits ambigus.
   - Impact: difficile de valider la qualité et d'accélérer les batches.
   - Correctif minimal: normaliser `verify=before;after;test` dans evidence.
