# BATCH-11 — Data Ingestion Core + Freshness SLO [ARCH]

## Architecture plan ref
- `docs/architecture/ARCHITECTURE_MAP.md`

## Objectif
Garantir une freshness mesurable (SLO) de bout en bout ingestion → API → UI, via des contrats stables et une observabilité minimale, sans dépendances top-level inter-batch.

## Décisions d’architecture
1) Contrat freshness (API)
   - Champs contractuels: `freshness_ts` (timestamp) + `freshness_status` (OK|STALE|UNKNOWN) + defaults.
   - Normalisation des payloads/erreurs dans `apps/api/runtime/` (pas dans UI).

2) Ingestion idempotente
   - Clé d’idempotence (source_id + window) pour retries; éviter doublons.

3) Observabilité
   - Métrique: `freshness_lag_seconds` (par source/endpoint) + seuil SLO.
   - Corrélation: `correlation_id` propagée req → logs/events.

4) UI
   - Afficher `STALE/OK/UNKNOWN` à partir du contrat (pas d’inférence locale).

## Architecture audit (paths impactés)
- `apps/api/runtime/` (normalisation, headers/correlation, erreurs)
- `apps/api/src/domains/*` (DTO/contrats/endpoints ingestion)
- `apps/web/src` (affichage freshness/erreurs)
- `platform/automation/` (preuves/gates uniquement)

## Acceptance gate
- SLO défini + métrique disponible + exemple payload conforme.
- Preuves: payload + capture métrique + scénario UI (ok/stale).

## Politique dépendances
- single batch; sequencing intra-batch uniquement (pas de depends_on_batch inter-BATCH-XX).
